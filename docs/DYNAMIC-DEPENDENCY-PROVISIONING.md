# Dynamic dependency provisioning

Status: **implemented** in the simplified, automatic form recorded in [ADR-010](decisions/ADR-010-dynamic-dependency-provisioning.md): there is no human dependency approval; the automatic PLAN policy validates requests. The design below remains the reference; the roadmap items not yet built are the per-attempt image digest pin, a resolver egress firewall and an offline vulnerability audit.

Core principle: **the agent may request dependencies; only trusted infrastructure acquires, verifies and prepares them. The coding sandbox stays offline.**

## 1. Current dependency architecture (audited 2026-11-25)

| Concern | Implementation (as found) |
|---|---|
| Execution image | `docker/execution/Dockerfile`: `python:3.12-slim` pinned by digest; `pip install --require-hashes --no-deps -r requirements.txt`; `pip check`. An operator builds it once; network is used at **build time only** |
| Inputs | `docker/execution/requirements.in` (hand-maintained). Each tool must be allowed by `CommandPolicy` |
| Lock | `requirements.txt` generated by `uv pip compile requirements.in --generate-hashes --python-version 3.12 --python-platform aarch64-unknown-linux-gnu`. Hashes enforced at install |
| Image selection | One global `WORKSPACE_IMAGE` (Settings → `composition._image`). Not per repository or profile, and not pinned per attempt |
| Profiles | `domain/repositories/profile.py`: `commands[]` with `kind` (test, lint, build, format, install), `toolchain`, `argv`, `network: none | package_registry`. `CommandPolicy` (default-v1) knows install rules (e.g. `npm ci --ignore-scripts` with network) |
| Blocking | `orchestration/steps.py::dependency_preparation` returns BLOCKED (`dependency_preparation_requires_network`) if any command is INSTALL or has `network != none`, and `no_execution_image_for_toolchain` for unknown toolchains |
| Worker ↔ sandbox | Worker host process → Docker CLI (`execution/docker/sandbox.py`, `runtime.py`): one bind mount, `/workspace` (`readonly` in planning), plus a `/tmp` tmpfs; `--network none` |
| Validation | Fresh network-less container; runs only profile commands re-checked against the policy |
| Artifacts | `ArtifactService` under `ARTIFACT_ROOT` (plans, manifests), content-hashed; not mounted into sandboxes |
| Dependency cache | **None** |
| Plan schema | `ImplementationPlan` has **no dependency field**; dependencies appear only in free text |

## 2. Current limitations

- Dependencies are known only when the image is built. A Story that needs a new package (found during planning) cannot be implemented or validated; at best it is BLOCKED.
- One image serves every repository: adding packages for one repository enlarges every sandbox and changes every repository's environment.
- The image is selected at run time, not pinned per attempt, so an approved attempt can run on a different image than the one it was planned on.
- The plan names dependencies only in prose, so the PLAN approval does not bind them structurally.

## 3. Dependency manifest design

A new `dependencies` section in `ImplementationPlan` (agent proposal) and a platform-produced **lock manifest** (trusted result).

### 3.1 Agent proposal (part of the plan, covered by the plan hash)

```json
{
  "schema_version": 1,
  "ecosystem": "python",
  "python_version": "3.12",
  "requested": [
    {"name": "fastapi", "specifier": "==0.165.0", "scope": "runtime", "reason": "HTTP API framework"},
    {"name": "httpx", "specifier": "==0.28.1", "scope": "test", "reason": "FastAPI TestClient"}
  ]
}
```

### 3.2 Lock manifest (trusted output, an immutable artifact)

```json
{
  "schema_version": 1,
  "plan_sha256": "<approved plan hash>",
  "repository_id": "<registry id>", "story": "KAN-7", "base_commit_sha": "<sha>",
  "target": {"python": "3.12", "implementation": "cp", "abi": "cp312", "platform": "manylinux_2_17_aarch64"},
  "index": "https://pypi.org/simple",
  "packages": [
    {"name": "fastapi", "version": "0.165.0", "direct": true, "filename": "fastapi-0.165.0-py3-none-any.whl",
     "sha256": "<hash>", "requested_by": ["plan"]},
    {"name": "starlette", "version": "1.10.0", "direct": false, "filename": "...whl", "sha256": "<hash>",
     "requested_by": ["fastapi"]}
  ],
  "lock_sha256": "<sha256 of the canonical JSON above>"
}
```

### 3.3 Validation rules (platform code, never trusting the model)

| Rule | Check |
|---|---|
| Name | PEP 508 name, normalised (PEP 503); rejects URLs, paths, VCS references, extras-injection and environment markers |
| Pinning | Exactly `==X.Y.Z` (PEP 440); no ranges, wildcards or `latest` |
| Duplicates / conflicts | One entry per normalised name; conflicting pins are rejected |
| Allowed scopes | `runtime` or `test` |
| Limits | At most N direct packages (e.g. 20) and M resolved (e.g. 150) |
| Policy | Optional deny list (known-malicious or typosquat names) and allow list per organisation |
| Python compatibility | Resolved `Requires-Python` must admit the target version |
| Transitives | Resolved by trusted infrastructure, recorded in the lock with `requested_by` |
| Hashes | Every file sha256; installation uses `--require-hashes` |
| Provenance | Index URL, resolver version, time, plan hash |
| Approval | Lock `direct` set must equal the approved plan's `requested` set |

## 4. Trusted preparation architecture (option B)

```
plan (agent, offline) ──► PLAN gate (human approves plan hash incl. requested deps)
          │
          ▼
worker: DependencyPreparer port ──► adapter: short-lived "resolver" container
          │                         (network: egress to the approved index only; no credentials of
          │                          the app; no workspace; no Docker socket)
          │                         pip download --only-binary=:all: --no-deps per resolved pin,
          │                         --platform/--python-version/--implementation/--abi
          ▼
worker verifies: lock ⇔ approved request, every wheel sha256, filenames match target tags
          │
          ▼
immutable bundle artifact  (wheels + requirements.lock + lock manifest)  ── cache key ──► reuse
          │
          ▼
sandbox (offline): bundle bind-mounted READ-ONLY at /deps;
pip install --no-index --find-links=/deps --require-hashes --no-deps -r /deps/requirements.lock
into a writable venv inside the workspace or tmpfs; the agent implements; validation repeats the
same offline install in its fresh container
```

The design follows the existing architecture:

- An application port `DependencyPreparer` (`application/dependencies/ports.py`) with one Docker adapter (`execution/docker/dependencies.py`).
- A pure domain validator (`domain/dependencies/manifest.py`).
- A new workflow step between PLAN approval and implementation.
- No new agent, service, queue or Redis.

Requirements met:

- **Outside the sandbox:** the resolver container is started by the worker and never runs agent code. It receives only the validated pin list. It downloads wheels only (`--only-binary=:all:`), so no `setup.py` or build backend ever executes, not even on the host.
- **Approved registries only:** an index allow-list (`DEPENDENCY_INDEX_URLS`, default PyPI). The resolver container can reach only that index, through a dedicated Docker network with an egress proxy, or the host firewall. Private registry credentials, if ever used, are passed only to the resolver container, never to the sandbox.
- **Resolution:** `uv pip compile` (already a dev dependency) with `--generate-hashes --python-platform <target> --python-version 3.12` on a generated `requirements.in` of the approved pins. This is the same proven process as the image lock.
- **Platform fit:** the target triple comes from the execution image (`python -c 'import sysconfig'`), recorded in the lock, and every wheel filename tag is checked.
- **Source-only or native builds:** no compatible wheel means **BLOCKED** (`dependency_wheel_unavailable`), with a request for a controlled build (an image update by an operator). There is never a fallback to sdist or network.
- **Bundle storage:** `ARTIFACT_ROOT/deps/<lock_sha256>/`, mode 0500/0400, written atomically (temp dir + rename), then never modified.

## 5. Artifact integrity model

1. The worker writes the bundle and computes the lock hash over the canonical lock JSON, which includes every wheel sha256.
2. Before each sandbox or validation start, the worker re-hashes every wheel against the lock (fail closed: `dependency_bundle_corrupted`), then bind-mounts the directory `readonly`.
3. The sandbox can't modify the bundle (read-only mount plus the non-root user). pip's `--require-hashes` re-verifies at install.
4. The attempt records `dependency_lock_sha256`. The FINAL manifest and validation record it too, so delivery proves which bundle was validated.

## 6. Offline installation process

```bash
python -m venv /workspace/.venv        # or /tmp/venv: tmpfs, never part of the changeset
python -m pip install --no-index --find-links=/deps --require-hashes --no-deps -r /deps/requirements.lock
python -m pip check
```

- The validation engine does the same in its fresh container.
- `.venv` is excluded from the changeset (it's already a non-source path; add it to protected or ignored paths).
- The sandbox keeps `--network none`. The install is offline by construction (`--no-index`); no network exists to fall back to.

## 7. Approval requirements

- The PLAN approval binds the plan hash. The plan now contains the structured `dependencies.requested` and the target environment (image digest and Python), together with the repository id, Story key and base commit that the attempt already binds.
- The preparer refuses any lock whose direct set differs from the approved request. Transitive packages are shown in the FINAL manifest and approved there.
- If the agent needs another package during implementation, it reports `blocked` with the request. The workflow produces a revised plan, which gets a new hash, so the previous approval is invalidated by construction, and a fresh PLAN approval is required.
- Pin the **image digest** per attempt (record it at attempt start), closing the "different image after approval" gap (section 2).

## 8. Cache design

- **Key:** `sha256(target triple + index URL + sorted(name==version + file sha256 for every package))`, i.e. the `lock_sha256`. Python version, OS, architecture and ABI are all inside the target triple.
- **Storage:** local filesystem under `ARTIFACT_ROOT/deps/<key>/`. Immutable after the atomic rename; read-only for every consumer.
- **Hit:** the directory exists and all hashes verify, so it's reused across repositories. A different hash is a different key, so a package can't be substituted.
- **Miss:** the same trusted preparation path.
- **Eviction:** an operator sweep by age (like workspaces); never mutate in place.
- No Redis, no new service.

## 9. Failure handling (all fail closed; attempt BLOCKED with a code)

| Code | Cause |
|---|---|
| `dependency_manifest_invalid` | name, pin, duplicate, scope or limit violation |
| `dependency_not_approved` | lock direct set ≠ approved request |
| `dependency_conflict` | resolver cannot satisfy pins together |
| `dependency_python_unsupported` | `Requires-Python` excludes the target |
| `dependency_wheel_unavailable` | only sdist or native build available → controlled build required |
| `dependency_hash_mismatch` | downloaded file ≠ locked hash |
| `dependency_index_not_allowed` | resolution referenced a non-allowed index or URL |
| `dependency_bundle_corrupted` | re-hash before mount failed |
| `dependency_preparation_failed` | resolver container error, timeout or size limit |

## 10. Supply-chain security

| Risk | Control |
|---|---|
| Prompt-injected Story asks for a malicious package | Human PLAN approval of the exact names and pins; deny list; limit on count |
| Typosquatting | Same, plus optional allow list; names shown normalised at approval |
| Install-time code execution | Wheels only, `--no-deps` from a pre-resolved lock; no sdist builds anywhere |
| Tampering after approval | Content hashes in the lock, re-verified before mount and by pip |
| Exfiltration | Sandbox stays `--network none`; the resolver never sees workspace content or the Story |
| Registry credential leakage | Credentials, if any, only in the resolver container's environment |
| Runtime malicious code in an approved package | Remains possible (it runs offline in the sandbox and validation). Mitigated by offline isolation, resource limits and human review. Consider `pip-audit` against an offline advisory DB as a later step |

## 11. Implementation roadmap (after ADR-010 approval)

1. **Domain:** `domain/dependencies/manifest.py` (request and lock models, validation), with unit tests.
2. **Plan schema:** `ImplementationPlan.dependencies` (optional, default empty) and prompt guidance; plan hash covers it.
3. **Port and adapter:**
   - `application/dependencies/ports.py` (`DependencyPreparer`, `DependencyBundleStore`);
   - `execution/docker/dependencies.py` (resolver container + verification);
   - the bundle store on `ARTIFACT_ROOT`.
4. **Workflow:**
   - a `prepare_dependencies` step after PLAN approval;
   - replace the blanket block in `steps.dependency_preparation` with "bundle ready or BLOCKED";
   - record `dependency_lock_sha256` and the image digest on the attempt (Alembic migration, forward-only).
5. **Sandbox and validation:**
   - optional read-only `/deps` mount in `sandbox_run_argv` and the validation runner;
   - an offline install command in the command policy (`pip install --no-index ...`, network none).
6. **Configuration:** `DEPENDENCY_INDEX_URLS`, size and count limits, preparation timeout.
7. **Docs:** update C2 in ARCHITECTURE-DECISIONS.md, plus SECURITY.md and ARCHITECTURE.md.
8. **Egress restriction** for the resolver container (Docker network + proxy, or host firewall rule), verified by an integration test.

## 12. ADR C2 impact

C2 stays true for the **coding sandbox** and the **validation container**: no network, ever. What changes is "when dependencies cannot be prepared offline the attempt is BLOCKED". The new rule: a trusted, agent-free resolver container with egress **only to approved package indexes** may prepare hash-locked wheels for **human-approved** dependencies. See ADR-010; this needs owner approval.

## 14. Test design (no real downloads)

| Case | Level | Expected |
|---|---|---|
| Valid manifest (2 pinned packages) | unit, domain | accepted, normalised names |
| Invalid name (`../x`, `git+https://...`, `pkg; os_name=="nt"`) | unit | `dependency_manifest_invalid` |
| Unpinned (`fastapi`, `>=1`, `==1.*`) | unit | rejected |
| Duplicate or conflicting pins (`Foo==1`, `foo==2`) | unit | `dependency_conflict` |
| Unsupported Python (`Requires-Python <3.10`) | unit with fake metadata | `dependency_python_unsupported` |
| Missing wheel (sdist only) | adapter with fake index (local dir) | `dependency_wheel_unavailable`, no build attempted |
| Hash mismatch | adapter, tampered wheel | `dependency_hash_mismatch` |
| Unexpected source (URL or non-allowed index in lock) | unit | `dependency_index_not_allowed` |
| Unapproved dependency (lock has an extra direct pin) | unit | `dependency_not_approved` |
| Changed after approval (plan edited) | workflow, in-memory | plan hash changes → approval invalid → gate re-opens |
| Cache hit | unit, tmp dir | same key, no preparer call, hashes re-verified |
| Cache miss | unit | preparer called once, bundle immutable (0400/0500) |
| Corrupted artifact (byte flipped after store) | unit | `dependency_bundle_corrupted`, no mount |
| Offline install | Docker integration, local wheelhouse fixture | install with `--no-index` succeeds under `--network none` |
| Sandbox network isolation with `/deps` mounted | Docker integration | outbound connection fails; `/deps` is read-only |
| Preparation failure (resolver exits non-zero or times out) | adapter, fake runner | `dependency_preparation_failed`, attempt BLOCKED |
| Native dependency (platform-specific only, wrong arch) | unit, fake index | `dependency_wheel_unavailable` |
| Resolver container has no app credentials or workspace | unit on argv | env and mounts asserted empty except the output dir |
